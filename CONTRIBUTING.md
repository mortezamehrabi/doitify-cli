# Contributing to Doitify CLI

This guide is for contributors and release maintainers. For installation and
everyday usage, see the [README](README.md) or visit [Doitify](https://doitify.com).

## Source setup

Use Node.js 22+ and keep the canonical `doitify-agent-workspace` checkout beside
this repository:

```text
DoitifyCLI/
├── doitify-agent-workspace/
└── doitify-cli/
```

Building and testing require access to that sibling source. Published npm users
receive a bundled instruction snapshot and do not need the source checkout.
Do not edit `dist/workspace/` directly; it is generated by
`scripts/bundle-workspace.mjs`.

Read `AGENT_RULES.md` and `feature.meta.json` before modifying the CLI.
Keep the package a dependency-free file installer, not an agent runtime.

## Preserve project data

Protected paths are defined by `userDataPaths` and `userDataDirectories` in
`src/init.mjs`. Extend protection before introducing a new agent-writable path.
Protection must take precedence over previously installed instruction hashes.

- Preserve project settings, knowledge, follow-ups, plans, reports and helpers.
- Never add a force-overwrite path or sweep unknown files.
- Preflight conflicts before any writes; keep dry-run entirely read-only.
- Test positive and negative cases, including legacy installs and customized data.
- Bundle only public starter indexes for user-owned folders. Never bundle
  private records, learned notes, generated scripts, credentials or local tooling.

Shared instruction changes belong in the canonical workspace, not a second
copy maintained inside the CLI.

`src/legacy-hashes.json` contains only public instruction hashes from verified
published tarballs, currently `@doitify/cli@0.1.0` and `0.1.2`. Both tarballs'
workspace manifest hashes were checked against their actual file bytes.
This enables offline migration without an installation baseline; it must never
override an existing recorded hash or include user data paths.

When adding release history, verify the official tarball's integrity and each
file hash, exclude every protected path, and add an offline regression fixture.
Never derive trusted migration hashes from an arbitrary local project. Creating
an absent user-owned folder may add its public starter, but an existing folder
and even its intentionally missing index must remain untouched.

## Local checks

From the CLI repository:

```bash
npm test
npm run check
npm pack --dry-run
```

Tests rebuild the workspace snapshot; packing also builds it through `prepack`.
Inspect the package file list and README before releasing. `check` performs
Node syntax validation; it is not a full linter.

For canonical instruction changes, also run its optional maintainer checks:

```bash
cd ../doitify-agent-workspace
python3 .doitify/.etc/check_bundle.py
```

These local checks do not prove OAuth, MCP tool availability, unattended
execution or compatibility with every operating system and agent client.

## Releases — authorized maintainers only

Do not publish without explicit release authorization. Review both repositories
and ensure the canonical source contains only public, unconfigured starter data.
Test the exact version and contents intended for publication.

From the CLI repository, for a patch release:

```bash
npm version patch --no-git-tag-version
npm test
npm run check
npm pack --dry-run
```

Choose `minor` for backward-compatible features and `major` for breaking changes.
Every npm release needs a new, unpublished version, including README-only updates.
Commit and push the reviewed source/version changes according to the release
process. Only then publish the verified package:

```bash
npm publish --access public
```

Publication requires permission for the `doitify` npm scope and authentication
satisfying npm's 2FA requirements. Use supported secure authentication; never
paste tokens into issues/chat or commit them to the repository.

After publishing, verify the version and `latest` tag in the registry. A Git push
alone does not update the npm package or its displayed README.
